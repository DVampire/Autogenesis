This is a **constraint-satisfaction** puzzle. No single clue identifies a class; the solution exists only when **every** clue is held at once, and each clue must be verified against an external source rather than recalled. The system does not have a memory system suited to this shape of task, and this run is to give it one. - Every clue must be verified with a `web_searcher_tool` query and its source cited before it counts. Answering from memorised game knowledge is not acceptable — the GAIA annotator used a browser and a search engine over 20 steps. - Handle one clue per step. Do not batch clues into a single pass. - Deliver evolved capabilities as extension components. Never modify `src/` or any built-in package file. - Do not hard-code the answer anywhere; it must come out of the deduction. The memory system the sub-agents are bound to is `file_system_memory`, a `TieredMemory`. Its retention policy is **chronological**: | Tier | Rule | |---|---| | `recent_fetch = 10` | only the last 10 records are injected verbatim | | `recent_max = 30` | beyond this the oldest 10 records are compacted into a summary | | `working_max = 10` | summaries are a bounded queue; the oldest is dropped | Every record ages out on the same schedule regardless of what it contains. A verified constraint and an incidental observation decay identically. That is the gap this task addresses: a constraint-satisfaction run needs retention keyed on **what a record is** — a confirmed constraint must never degrade while the puzzle is open — not on **how old it is**. Chronological tiering does not provide that, and no amount of re-prompting the agent supplies it, because the policy lives in the memory resource. ``` final answer == "Death Knight, Hunter, Paladin, Priest, Warlock" ⇒ pass anything else ⇒ fail ``` A new memory component must exist under `extension/memory/`, and the memory the agents are actually bound to must end the run carrying the constraint-preserving policy.
