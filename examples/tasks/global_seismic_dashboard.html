Task: Global earthquake situational-awareness dashboard (capability-building)

Build a polished, single self-contained HTML dashboard that turns real, recent global earthquake data into a situational-awareness briefing: where the significant quakes were, how strong, how much energy they released, how close they struck to major population centers, and what the spatial/temporal/magnitude patterns are.

This is deliberately a domain the system has no ready-made capabilities for (the loaded connectors are all bio/chem/genomics; there is no geospatial tool and no seismic methodology skill). Treat that as the point of the exercise: where a capability is genuinely missing, evolve a new, reusable capability of the right type into extension/ — then actually use it to produce the deliverable. Follow the self-evolving playbook (decide → generate → evaluate → adopt or roll back); do not hand-wave capabilities you never built.

Capabilities you are expected to build (each a real, registered extension component)

  1. A connector for a public seismic data feed (e.g. the USGS earthquake GeoJSON feeds at earthquake.usgs.gov, which need no auth). Build it as a proper reusable connector — not a one-off web_fetcher call — so the capability persists and is inspectable. It must fetch a bounded feed (e.g. magnitude ≥ 4.5, past 30 days).
  2. A tool for the geospatial/seismic math this domain needs and that no existing tool provides: great-circle (haversine) distance from a quake to the nearest of a fixed list of major cities, and an approximate energy-release estimate from magnitude (e.g. log10 E ≈ 1.5·M + 4.8, in joules). Reusable, with a clean structured data result.
  3. A skill capturing the analytical methodology so the report is systematically rigorous rather than ad hoc: how to characterize a seismic catalog — spatial distribution, temporal trend, the magnitude–frequency (Gutenberg–Richter) relationship, and proximity-to-population exposure — and how to present it honestly.

If, while building, a sub-agent hits a recurring structural failure (same fault ≥2×), optimize the responsible agent/prompt rather than retrying blindly. For every capability you create or change: evaluate it, keep it only if it demonstrably helps, and roll it back with the evolution tool if it does not. Report explicitly what you evolved and why.

The deliverable

  • A single self-contained seismic_dashboard.html that opens standalone — every figure embedded inline as a data: URI, no external files needed.
  • Content, every claim backed by a number you actually computed from the fetched data:
    • Headline stats: event count, date range covered, largest quake (magnitude, place, estimated energy), and total estimated energy released.
    • A spatial view (a lon/lat scatter or simple inline map) sized/colored by magnitude.
    • A temporal view (events per day over the window).
    • A magnitude–frequency plot and the fitted Gutenberg–Richter b-value.
    • A proximity table: the N largest quakes and the nearest major city with its great-circle distance (computed by your new tool).
    • An honest limitations section (feed completeness, magnitude thresholds, sampling).
  • Verify the dashboard hands-on with the browser agent: it renders, all figures are visible, and the console is free of errors.

Hard constraints (read before fetching data)

  • Bound the data. Use a filtered feed (magnitude ≥ 4.5, past 30 days) — on the order of tens to a few hundred events, not the full firehose.
  • Never read a raw data file into the conversation. Do NOT cat / print whole JSON/CSV files. Process data with scripts and print only compact summaries (≤ ~50 rows or ≤ ~2 KB at a time). Oversized dumps into context are a hard failure.
  • If the seismic feed is unreachable from this environment, say so explicitly and fall back to a small bundled sample, but still build the connector/tool/skill as specified.
  • Keep the whole run within a sensible budget; if it gets tight, finish the deliverable with the capabilities you already have rather than starting new evolution rounds.

Acceptance criteria

  • A self-contained seismic_dashboard.html that opens standalone with all figures visible and verifies as self-contained.
  • It is built on real fetched seismic data — state the event count and date range.
  • At least three new extension components of different types (a connector, a tool, and a skill) were generated, registered, evaluated, and actually used — listed in the report with their evaluation verdicts.
  • The analysis (b-value, energy, distances, trends) is backed by actual computed values.
